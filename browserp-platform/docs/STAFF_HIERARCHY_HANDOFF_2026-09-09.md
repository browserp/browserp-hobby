## Authority, restrictions and privacy

Staff assignment, role editing, override changes and account enforcement require a valid current write session and current effective permission. They reject self, peer and superior targets. The target rank is the maximum stored membership/mapping rank, including inconsistent mappings; the current schema permits one membership per account. Governance permissions have minimum rank floors, and granting a lower role or reactivating a member checks the resulting default permissions plus retained overrides. Resetting an override checks the permission that the default would restore.

Moderator and Senior Moderator restrict accounts only. Admin and higher may also restrict device or network targets. Finite restrictions have a five-minute minimum and the exact rank limits above. Reversing another staff member's restriction requires authority strictly above the original issuer's current rank, or the original issuer can reverse their own action, subject to current target hierarchy. Expired restrictions stop blocking access without waiting for a background job.

Implementation decision for Main's review: restrictions connected by overlap or by a gap of at most five minutes after the previous scheduled end retain their earliest episode start. Early revocation and immediate reapplication cannot restart a same-tier or lower-tier limit. Strictly higher authority may approve a new window. More than five clear minutes beyond the previous scheduled end permits a separate episode. This continuity interval is an implementation choice disclosed to Main, not a duration explicitly selected by George.

Protected network evidence stays masked by default. Owner, Management and Head Admin can approve requests or make an audited direct view; other staff need the relevant permission and a valid approved, time-limited, single-use request. Self-approval is rejected. The public privacy and legal pages describe this matching behavior and should ship with the corresponding backend and UI.

Account erasure remains a count-only review with execution disabled. The new private staff-change request records are included in the requester's bounded account copy without replacing the existing content-moderation export sections. No erasure executor, retention change or external backup claim is included.

The canonical persistent staff predicate validates an undeleted, non-anonymous account, exactly one Discord identity, an enabled matching allowlist entry, an active same-role membership and no current account restriction. It deliberately does not require the member to be online or have a current session merely to display staff recognition. Staff actions still require their own current session/MFA checks. All direct client execution privileges on the helper are revoked.

## API contract

- `GET /api/admin/roles`: existing control envelope; adds independent `actorRank`, `canAssign`, `canEditRoles`, `canRequest`, `canReviewRequests`; each role includes `assignable` and `editable`.
- `GET /api/admin/staff`: `{ staff }`; members include `userId`, current `rank` and `manageable`. Non-managers see their own member entry. The role catalogue is available independently.
- `GET /api/admin/staff?view=requests`: `{ requests }`; each request has `version` and `canReview`. Latest own/actionable records are bounded to 50.
- `POST /api/admin/staff`: existing direct action; `requestAction: "create"` adds a reviewed request with a stable UUID `requestKey`; `requestAction: "decide"` uses request `id`, `expectedVersion`, boolean `approved` and a reason. Database review calls the same current direct-assignment guard.
- `POST /api/admin/permissions`: requires the current staff `expectedVersion` and strict boolean or null `allowed`. The response includes the new `result.version`. The old unversioned five-argument RPC has no client execute grants.
- `GET /api/admin/bans?view=access`: `{ access: { rank, maxMinutes, canIndefinite, canDeviceNetwork } }`.
- `POST /api/admin/bans`: `restrict_account` accepts `userId`; activity-based `apply` accepts `activityId`, `targetType` and `scope`. Both require explicit integer `minutes` or null for indefinite. Duration, hierarchy and device/network authority are enforced again in SQL.
- Security status provides `canApproveNetwork` and `canRequireMfa`; erasure visibility uses `reviewErasure`. Literal `isOwner` is preserved for its original meaning.

`control.permissions` continues to contain the actor's effective permission descriptions; no new `canDelegate` field was added there. Per-person permission control includes `delegatable` and `minimumRank`. Chat5's delivered field/action names match these contracts. Authentication, same-origin checks, reasons, versions and private/no-store responses remain in the shared router; no additional serverless route surface was introduced.
