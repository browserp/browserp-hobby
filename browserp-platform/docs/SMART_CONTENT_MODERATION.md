# Guarded content moderation

This change covers comments/replies, display-name edits, prepared avatar uploads and the first imported OAuth name/avatar. Server applications retain manual review. It introduces no audit fee, appeal fee, public confidence badge or automatic reputation label.

Automated classification requires both an explicit `CONTENT_MODERATION_PROVIDER=openai` setting and a valid server-side `OPENAI_API_KEY`. Reuse the existing configured key; its presence alone does not enable the checker. This readiness change does not activate the provider. Missing configuration, an unavailable checker, malformed results, unsupported coverage and uncertain results all leave the content privately pending for staff. Local word/link/duplicate patterns only request review; they do not certify safety or prove abuse. Even with OpenAI enabled, pictures never automatically publish because its image category coverage is incomplete. A supported clear image finding may block a picture, and the member can ask staff to review that decision for free.

## Publication and authority

`20260909092918_guarded_content_moderation.sql` was generated with `npx --yes supabase@2.117.0 migration new guarded_content_moderation`. It creates `private.content_submissions`, indexed private queues and narrowly granted member/staff/service RPCs. The table is RLS-enabled and has no client grants. Member writes retain the existing account/session/ban/quota controls and repeat `private.require_member_write_session` after waits and writes. Staff decisions retain the existing `moderation.resolve` or `profiles.review` permission, Discord/MFA/session checks and final authorization checks after the audit write.

A submission's text or frozen asset, owner, fingerprint and version come from the database. The service role can record a checker result; it cannot publish through a member wrapper. An active owner then consumes that exact saved result through a separately granted RPC. A browser-supplied decision, score, owner or fingerprint has no authority. NULL, unsafe integer and stale versions cannot authorize a transition. A later edit, replacement or staff decision invalidates an older check. Staff can block a published record after a report; a current blocked picture is removed from the public profile and its asset is marked rejected. A new independent block of previously published content has a new free appeal opportunity. Resolving an appeal uses the ordinary staff approve/block action.

Public profiles retain their prior approved identity while replacements wait. A new OAuth profile initially publishes the safe name “BrowseRP member” and no picture. Approved replacement identities supersede earlier private publication records. Existing public identities and published comments are not retrospectively reclassified by this migration. Existing pending comments are brought into the new private review records. Existing staff comment decisions synchronize the private status/version, including later hide/reject/restore operations.

## Private media

Prepared member PNGs retain the existing full raster validation and 512 × 512 / 1 MiB limits. Files are registered first, then uploaded server-side to the existing private `uploads-quarantine` bucket with unique owner-bound paths and SHA-256 hashes. No client upload permission is added. Interrupted writes remain registered for existing storage/erasure review; this feature does not introduce a new storage cleanup schedule.

Imported OAuth pictures are fetched only from the two existing allowlisted provider hosts (`cdn.discordapp.com`, `lh3.googleusercontent.com`) with no redirects, a four-second fetch timeout and a one-MiB streamed limit. Only recognized PNG/JPEG/WebP images are retained; PNG animation is reduced using the existing static PNG verifier. The exact private bytes are frozen before checking/review. An unsupported or unavailable imported picture stays pending with an instruction to upload a replacement. The private source URL is not returned to the member or staff UI. OAuth sign-in remains available if preparation/checking fails.

Approved image URLs use `https://www.browserp.com/api/public/profile-avatar?id=<submission UUID>`. The public route verifies that the exact submission remains published and is the profile's current approved picture both before and after loading bytes. Both public and private delivery use `private, no-store`, `nosniff` and a restrictive image response policy. Private previews require the active owner or staff with `profiles.review`. Neither route returns the storage path/key, signed storage URL or provider URL. Stored byte count, hash and detected type must match on delivery. The new canonical avatar path must be served by the integrated deployment before approved images can render, including previews that reference the canonical host.

## HTTP contract

All review JSON uses the existing private no-store response wrapper. Collection pages contain at most 20 records, use indexed keyset cursors and do not perform total-count scans. `nextBefore` is either null or a serialized JSON string containing `{createdAt,id}`; pass that exact string as the URL-encoded `before` query parameter, preserving timestamp precision.

- `GET /api/me/content-moderation?before=...` returns `{items,nextBefore}` for the active member.
- `POST /api/me/content-moderation` accepts `{id,action:"appeal",statement,expectedVersion}` and returns `{item}`. A blocked decision has one appeal; staff resolution does not incur a fee.
- `GET /api/admin/content-moderation?kind=all|comment|display_name|avatar&before=...` returns the pending review/appeal queue permitted for the staff member. No status/limit parameter is needed. The optional `id=<UUID>` lookup returns one permitted item for a report or revocation review.
- `POST /api/admin/content-moderation` accepts `{id,action:"approve"|"block",reason,expectedVersion}` and returns `{item}`.
- `GET /api/content-moderation/preview?id=<UUID>` serves private bytes after owner/staff checks.
- `GET /api/public/profile-avatar?id=<UUID>` serves only a current approved picture.

Items have `id`, `kind`, `targetId`, `status`, `reason`, `version`, `createdAt`, `appealStatus`, `appealStatement`, `text` and `previewUrl`. Staff items also identify the owner. Statuses are `pending_review`, `published`, `blocked`, `superseded`; appeal statuses are `none`, `pending`, `resolved`. A canonical avatar item has `text:null`; the adapter boundary omits text when classifying its bytes.

Existing comment/profile/avatar POST responses add `moderation`. Avatar `avatarUrl` and returned public profile values remain the previous approved values while pending. Comment database `rejected` maps to moderation status `blocked`; public comments still use their existing published-only projection. Existing bio review is separate and remains manual.

## Checker policy and operational bounds

The adapter makes one request to the fixed OpenAI moderation endpoint with pinned model `omni-moderation-2024-09-26`. It does not follow redirects, retry, use client-chosen endpoints/models or run a background polling loop. Text is at most 1,000 characters, image bytes at most 1 MiB, provider responses at most 64 KiB streamed, and the provider deadline at most four seconds. The orchestration applies a twelve-second signal to database/storage work and a separate two-second final active-owner readback; an already running classifier still has its independent four-second deadline. Existing endpoint and distributed quotas remain active. Review endpoints use 60 reads or 20 mutations per five minutes; member appeal RPC additionally retains a six-per-hour quota. Picture delivery uses 120 requests per five minutes.

The default policy approves text only with complete schema/category coverage, all category scores <= 0.01, no provider flags and no local review/obfuscation concern. Blocking requires a supported category flag and score >= 0.95 in the narrowly configured block categories. Broad violence, illicit activity, self-harm and self-harm-intent signals alone remain review because game discussion and help-seeking can trigger them. All intermediate results remain pending. Optional settings allow stricter thresholds only: `CONTENT_MODERATION_SAFE_THRESHOLD` 0..0.01; `CONTENT_MODERATION_BLOCK_THRESHOLD` 0.95..1; `CONTENT_MODERATION_TIMEOUT_MS` 50..4000. Invalid configuration fails to private review. Scores are model signals, not calibrated certainty, and thresholds need evaluation against representative synthetic/approved fixtures before activation.

The provider does not supply a general spam or impersonation category. Existing duplicate/link/name rules and quotas remain useful review signals, but this version does not claim complete automatic spam or picture-safety coverage. No external call with real member content was made during implementation/testing.

## Disclosure and activation

The member-facing disclosure in `public/privacy.html#content-review` uses conditional language that remains true before and after deliberate activation. It identifies OpenAI, submitted comments/names/pictures and imported OAuth identities, explains private uncertainty and mandatory staff picture approval, and preserves previous approved identity and free appeals. Publish this disclosure with the working moderation routes before live external transmission. It does not claim either current sending or current no-sending. The adapter adds no account details or browsing history to its input; submitted text or pictures can themselves contain personal information.

The [OpenAI moderation guide](https://developers.openai.com/api/docs/guides/moderation) describes the endpoint as free and documents incomplete image-category coverage. [OpenAI's data-controls table](https://developers.openai.com/api/docs/guides/your-data) currently lists `/v1/moderations` as not used for training, with no abuse-monitoring or application-state retention. Verify the account's actual access, rate limits, contractual terms and any applicable regional/data-handling requirements before sending member content. This patch neither verifies account availability nor activates billing/configuration. Hosting/database/storage usage still exists.

The private database stores the content needed for review, bounded decision metadata, status/version and current appeal statement. It does not store raw provider error bodies or credentials. Profile/account and comment deletion cascade the corresponding private submission records. Storage media and data-export/retention mapping must be verified through the existing privacy/erasure workflow before launch; there is no new automatic retention schedule in this patch. Avoid promising a retention duration until the owner approves it.

## Verification and release boundary

### Synthetic text activation evaluation

`scripts/evaluate-content-classifier.mjs` imports the actual pinned classifier and the server's local signal adapter. Its only content input is `test/fixtures/content-classifier-synthetic.json`: 18 handwritten synthetic cases covering ordinary comments/names, negative criticism, quotations, roleplay and help-seeking context, review signals, obfuscation and clear threats. Context cases allow either approval or review while disallowing blocking; strict review/approval/block cases retain their individual labels. These are expected policy routes for evaluation, not assertions that the model already produces them.

Main runs the evaluator after securely supplying the existing key in the process environment. Keep the deployed provider flag unset. From `browserp-platform`, the explicit command is:

```text
node scripts/evaluate-content-classifier.mjs --run
```

Without `--run`, the script displays usage and makes no request. It accepts no content, input-file, image, model or endpoint arguments. It passes an invocation-local provider setting to the real classifier without changing `process.env` or deployment configuration. Existing safe/block/timeout settings, when supplied, still pass through the classifier's validation and stricter-only bounds; omitted settings use the unchanged defaults. There is no new service or runtime text-only mode.

The run is sequential with at most one request per fixture and a hard fixture ceiling of 20. Each request retains the classifier's maximum four-second deadline and response cap. The runner stops on the first operational, schema or configuration error and never retries. Routing mismatches are recorded while the remaining cases run once. Standard output is a JSON receipt with fixture IDs, expected/actual routes, timings, sanitized error codes and completion/pass status; it contains no text, images, keys, raw responses or error bodies. Exit status is nonzero for an incomplete run or any unexpected route. Protect the key through the existing secure environment mechanism; never put it in command arguments or a receipt.

Review the receipt against the fixed labels and resolve false approvals/blocks before activation. A passing small synthetic set establishes only those cases under the tested configuration; it is not a complete accuracy, spam or picture-safety claim. The focused offline privacy tests exercise the runner using mocks, not OpenAI. No provider request was made to prepare this patch.

### Hosted activation gate

Focused synthetic tests cover strict provider schemas and failure cases, real classifier + canonical avatar mapping, private API orchestration, storage access/hash/size/type checks, owner/staff/anonymous SQL grants, stale/NULL versions, replies/duplicates, OAuth first publication, free appeals, published-image removal, and rollback when delays cross session expiry during comment/profile/avatar/check/appeal/audit writes. PostgreSQL runs in disposable PGlite using relevant existing tables/functions and the complete new migration; this does not prove the entire hosted migration chain or production Storage policy state.

Before release, Main must integrate the UI with this backend, run the required focused delta review at the frozen commit, and verify the migration against a controlled environment. Then read back real RPC grants, RLS, the private quarantine bucket and member/staff fixture behavior. An immutable preview needs the new API routes and migration together. Automated classifier activation additionally requires the explicit provider setting, existing key, published disclosure and evaluated thresholds. `CONTENT_WRITES_PAUSED` does not pause OAuth import checks, so keep the live provider flag unset throughout synthetic evaluation. The single runtime flag enables picture checking as well as text; pictures still cannot auto-publish. Previously checked pending submissions are not automatically retried when the flag changes and remain with staff review. No hosted migration, production configuration change or provider call is part of this readiness patch.

### Controlled promotion and rollback

This change has no safe mixed-version window for profile-picture writes. The migration deliberately revokes the old `member_set_profile_avatar(text,uuid)` function because the old application uploads into the public `profile-media` bucket and immediately publishes that URL. Accepting those uploads through a compatibility bridge would defeat the private-review boundary. The old comment client is compatible with the new migration: it already treats a successful response as sent for moderation, and the replacement comment RPC returns a private pending result.

Main should use one controlled maintenance promotion for member content writes: stop profile, picture and comment mutations; apply and verify the migration; deploy the exact integrated application and its canonical avatar routes; then verify signed-in profile, picture and comment fixtures plus staff exact-version decisions before reopening writes. Keep `CONTENT_MODERATION_PROVIDER` unset during this promotion; retain the existing server key. Enable the provider only after the disclosure, synthetic evaluation and existing release checks are complete. Legacy staff comment decisions are rejected in both deployment layers: the application routes reviewers to Content review, and the migration refuses queue-only decisions for enrolled comments.

Before the migration is applied, the application can be rolled back to the previous release normally. After the migration is applied, do not restore the previous application while member writes are open. If the application promotion fails, keep those writes in maintenance and either complete the forward deployment or use a separately reviewed compatibility migration; do not restore immediate avatar publication, drop private submissions or replay queue-only approvals. Existing approved profile values and published comments remain available throughout this process.
